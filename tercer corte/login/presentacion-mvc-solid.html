Arquitectura

¿Qué es el patrón MVC?

MVC separa una aplicación en tres responsabilidades bien definidas para facilitar el mantenimiento, la escalabilidad y las pruebas.

🗄️

Model

Representa los datos y las reglas de negocio. No sabe nada de la interfaz ni de cómo se persisten los datos.

🖥️

View

Es la interfaz de usuario. Muestra información y captura eventos. No conoce ni modelos ni repositorios.

⚙️

Controller

Orquesta la comunicación entre la View y el Model. Contiene la lógica de negocio.

Arquitectura extendida

MVC Extendida: capas adicionales

El MVC clásico coloca toda la lógica de acceso a datos en el Model. Nosotros lo extendemos separando esa responsabilidad en capas dedicadas.

➕ Repository Layer

Aísla completamente el acceso a datos (CSV, base de datos, API...). El Controller nunca sabe cómo se guardan los datos, solo pide y recibe.

➕ Services Layer

Lógica transversal que no pertenece a una entidad específica. En nuestro caso: SessionService gestiona el usuario activo en toda la app.

Models/

Solo almacenan datos. Sin lógica, sin acceso a archivos, sin UI.

Controllers/

Validan, transforman y coordinan. Devuelven strings o List<string[]> a la View.

Respository/

Leen y escriben archivos CSV. Son los únicos que conocen el medio de persistencia.

Services/

Estado compartido entre formularios. SessionService guarda usuario y rol activos.

Views/

Solo UI. Hablan únicamente con Controllers, nunca con Models ni Repositories.

✅ Lo que SÍ hacemos

  • View llama a métodos del Controller
  • Controller usa el Repository internamente
  • Controller devuelve string o List<string[]> a la View
  • Repository trabaja con Models para leer/escribir

❌ Lo que NO hacemos

  • View importando login.models
  • View llamando directamente al Repository
  • View recibiendo objetos Model (ClienteModel, etc.)
  • Repository usando clases de la View

// Clase base — solo datos de persona
class PersonaModel
{
    public string Nombre   { get; set; }
    public string Apellido { get; set; }
    public string Cedula   { get; set; }
    public string Email    { get; set; }

class UsuariosModel : PersonaModel
{
    public string Usuario  { get; set; }
    public string Password { get; set; }
    public string Rol      { get; set; }
}

class ClienteModel : PersonaModel
{
    public string   NumeroCliente { get; set; }
    public DateTime FechaRegistro { get; set; }
}
Diseño orientado a objetos

Principios SOLID

SOLID es un conjunto de 5 principios formulados por Robert C. Martin que guían el diseño de software orientado a objetos robusto, mantenible y escalable.

S

Single Responsibility

Una clase, una razón para cambiar

O

Open / Closed

Abierto para extender, cerrado para modificar

L

Liskov Substitution

Las subclases no rompen el contrato base

I

Interface Segregation

Interfaces pequeñas y específicas

D

Dependency Inversion

Depender de abstracciones, no de implementaciones

SOLID
S

Single Responsibility Principle

"Una clase debe tener una sola razón para cambiar."

Si una clase hace demasiadas cosas, un cambio en una responsabilidad puede romper las otras. La solución es separar cada responsabilidad en su propia clase.

En nuestro proyecto:

  • PersonaModel — solo almacena datos de persona
  • UsuariosRepository — solo lee/escribe el CSV de usuarios
  • ClienteController — solo orquesta la lógica de clientes
  • SessionService — solo gestiona la sesión activa
  • LoginForm — solo maneja el formulario de inicio de sesión
// ✅ Bien: cada clase tiene una sola responsabilidad

// Solo guarda/lee CSV de usuarios
class UsuariosRepository
{
    public void Crear(UsuariosModel u) { ... }
    public List<UsuariosModel> ObtenerTodos() { ... }
    public void Actualizar(UsuariosModel u) { ... }
    public void Eliminar(string usuario) { ... }
}

// Solo gestiona la sesión activa
static class SessionService
{
    public static string Usuario { get; private set; }
    public static string Rol     { get; private set; }
    public static void Session(string u, string r)
    { Usuario = u; Rol = r; }
}
SOLID
O

Open / Closed Principle

"El código debe estar abierto para extensión, pero cerrado para modificación."

Cuando necesitamos nueva funcionalidad, debemos poder agregar código nuevo sin modificar el código que ya existe y funciona.

En nuestro proyecto:

  • PersonaModel nunca fue modificada al agregar usuarios o clientes
  • Se crearon UsuariosModel y ClienteModel extendiéndola
  • Si mañana se agrega EmpleadoModel, PersonaModel sigue intacta
  • El sistema de CSV puede cambiarse a una base de datos sin tocar los Controllers
// PersonaModel: CERRADA para modificación
class PersonaModel
{
    public string Nombre   { get; set; }
    public string Apellido { get; set; }
    // ... nunca hay que cambiar esto
}

// UsuariosModel: ABIERTA para extensión
class UsuariosModel : PersonaModel
{
    public string Usuario  { get; set; }
    public string Password { get; set; }
    public string Rol      { get; set; }
}

// EmpleadoModel: también extiende sin tocar la base
class EmpleadoModel : PersonaModel
{
    public string Cargo   { get; set; }
    public decimal Salario { get; set; }
}
SOLID
L

Liskov Substitution Principle

"Los objetos de una subclase deben poder reemplazar a los de la clase base sin romper el programa."

Una subclase debe cumplir el contrato de su clase padre. No debe cambiar comportamientos ni lanzar excepciones inesperadas.

En nuestro proyecto:

  • UsuariosModel y ClienteModel extienden PersonaModel respetando su contrato
  • Ambas son construibles con los mismos datos base (nombre, apellido, cédula, email, teléfono)
  • Cualquier código que use PersonaModel funciona igual con sus subclases
// El contrato de PersonaModel:
// constructor acepta los 5 campos básicos
class PersonaModel
{
    public PersonaModel(
        string nombre, string apellido,
        string cedula,  string email,
        string telefono) { ... }
}

// UsuariosModel respeta el contrato base:
class UsuariosModel : PersonaModel
{
    public UsuariosModel(
        string nombre, string apellido,
        string cedula,  string email,
        string telefono, // ← base
        string usuario, string password,
        string rol)
        : base(nombre, apellido, cedula, email, telefono)
    { ... }
}
SOLID
⚠️ Cumplimiento parcial
I

Interface Segregation Principle

"Ningún cliente debería ser forzado a depender de métodos que no usa."

✅ Lo que sí cumplimos

  • La View recibe List<string[]>, no modelos completos
  • Cada Controller expone solo los métodos que su View necesita
  • ClienteController y UsuariosController son independientes

❌ Lo que nos falta

  • No existen interfaces IUsuariosRepository ni IClienteRepository
  • Los Controllers conocen la clase concreta del Repository, no un contrato
  • Sin interfaces no se pueden segregar ni intercambiar implementaciones

💡 La solución sería crear una carpeta Interfaces/ con IUsuariosRepository e IClienteRepository, y que los repositorios las implementen.

// ❌ Lo que tenemos: el Controller conoce
// la clase concreta directamente
class ClienteController
{
    private ClienteRepository repo
        = new ClienteRepository();
}

// ✅ Lo que debería ser: depender de
// una interfaz, no de la implementación
interface IClienteRepository
{
    void Crear(ClienteModel c);
    List<ClienteModel> ObtenerTodos();
    void Actualizar(ClienteModel c);
    void Eliminar(string id);
}

// Y ClienteRepository implementaría esa interfaz
class ClienteRepository : IClienteRepository
{ ... }
SOLID
⚠️ Cumplimiento parcial
D

Dependency Inversion Principle

"Los módulos de alto nivel no deben depender de los de bajo nivel. Ambos deben depender de abstracciones."

✅ Lo que sí cumplimos

  • La View depende solo del Controller, nunca del Repository
  • La View nunca importa login.models ni login.Respository
  • El flujo View → Controller → Repository → CSV respeta las capas

❌ Lo que nos falta

  • Los Controllers instancian directamente: new UsuariosRepository()
  • Dependen de la clase concreta, no de una abstracción (interfaz)
  • Si se cambia CSV por SQL, habría que modificar el Controller
  • No hay inyección de dependencias — el Controller crea su propia dependencia

💡 La solución sería inyectar el repositorio por constructor: public UsuariosController(IUsuariosRepository repo). Así el Controller nunca sabe qué implementación usa.

// ❌ Lo que tenemos: acoplamiento fuerte
// El Controller crea su propia dependencia
class UsuariosController
{
    private UsuariosRepository repo
        = new UsuariosRepository(); // ← problema
}

// ✅ Lo que debería ser:
// inyección de dependencias por constructor
class UsuariosController
{
    private readonly IUsuariosRepository repo;

    // La dependencia llega desde afuera
    public UsuariosController(IUsuariosRepository repo)
    {
        this.repo = repo;
    }
    // Ahora podría recibir CsvRepository,
    // SqlRepository o cualquier otro sin cambiar nada
}
Resumen

SOLID aplicado en nuestro proyecto

• Principio Dónde se aplica Evidencia en el código
S Single Responsibility Todas las capas Cada clase tiene una sola función: Models = datos, Repository = CSV, Controller = lógica, Service = sesión
O Open / Closed Jerarquía de Models PersonaModel nunca se modifica. Se extiende con UsuariosModel y ClienteModel
L Liskov Substitution Herencia de modelos Las subclases llaman a base(...) respetando el constructor de PersonaModel
I Interface Segregation ⚠️ PARCIAL ✅ Views reciben List<string[]>, no modelos completos.
❌ No existen interfaces IUsuariosRepository ni IClienteRepository. Los Controllers conocen la implementación concreta.
D Dependency Inversion ⚠️ PARCIAL ✅ La View no depende del Repository ni de los Models.
❌ Los Controllers instancian new UsuariosRepository() directamente. Falta inyección de dependencias e interfaces.
Conclusiones

¿Qué logramos con esta arquitectura?

🔧

Mantenibilidad

Cada cambio impacta solo la capa correspondiente. Cambiar de CSV a base de datos solo modifica el Repository.

📦

Escalabilidad

Agregar una nueva entidad (Empleado, Proveedor...) sigue el mismo patrón sin tocar el código existente.

🧩

Separación clara

Cada desarrollador puede trabajar en su capa sin interferir con los demás. La View no necesita saber de modelos.

La combinación de MVC extendida con los principios SOLID produce código que es fácil de entender, fácil de cambiar y difícil de romper.
